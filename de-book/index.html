01 · Window Functions

How to use this chapter: read the concepts, then for each problem write your query on paper (or just in your head) before opening Show answer. The comments inside each answer explain the trap it's testing. The tables used are described in 00 The Practice Data.

Practice problems: W1–W10 · Time: ~3 hours

The mental model

GROUP BY collapses rows: 50 orders become 13 customer rows. A window function keeps every row and adds a column computed from a set of related rows (the window).

function(...) OVER (
    PARTITION BY a, b      -- which rows belong together (like GROUP BY, but no collapse)
    ORDER BY c             -- order inside each partition
    ROWS BETWEEN ... AND ... -- the frame: which rows, relative to the current one
)

When a query runs, window functions are evaluated after WHERE, GROUP BY and HAVING, and before ORDER BY and LIMIT:

FROM/JOIN → WHERE → GROUP BY → HAVING → WINDOW FUNCTIONS → SELECT → DISTINCT → ORDER BY → LIMIT

That order has three consequences you will use constantly:

  1. You cannot use a window function in WHERE. Compute it in a CTE, then filter outside. (BigQuery has QUALIFY for this: QUALIFY ROW_NUMBER() OVER (...) = 1.)
  2. WHERE changes what the window sees. WHERE status = 'completed' means LAG never sees cancelled orders. Sometimes you want that, and sometimes you need to filter in an outer query instead (see D5).
  3. You can window over an aggregate. SUM(SUM(amount)) OVER (...) is legal, but a CTE is clearer.

Top-N per group: the most common window question

WITH ranked AS (
    SELECT *, RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk
    FROM employees
)
SELECT * FROM ranked WHERE rnk <= 3;

LAG / LEAD: look at neighbouring rows

LAG(col)             -- previous row's value (NULL for the first row)
LAG(col, 2)          -- 2 rows back
LAG(col, 1, 0)       -- default 0 instead of NULL
LEAD(col)            -- next row

⚠️ LAG means "previous ROW", not "previous MONTH". If a customer ordered in Feb and Jun, then in June LAG returns February. When the question says "previous month", you need either a calendar spine or a join on the exact previous month. This trap is the core of problem X1.

Aggregate windows: SUM / AVG / COUNT / MIN / MAX OVER

SUM(amount) OVER (PARTITION BY customer_id)                     -- customer total, on every row
SUM(amount) OVER (PARTITION BY customer_id ORDER BY order_date) -- running total
AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) -- moving avg
100.0 * salary / SUM(salary) OVER (PARTITION BY dept)           -- % of group

Frames: the part most people get wrong

You writeThe frame is
OVER (PARTITION BY x) (no ORDER BY)the whole partition
OVER (... ORDER BY y) (no frame)RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, i.e. start of the partition through the current row and all its ties
ROWS BETWEEN 6 PRECEDING AND CURRENT ROWthe current row plus the 6 physical rows before it
RANGE BETWEEN 6 PRECEDING AND CURRENT ROWrows whose ORDER BY value is within 6 of the current one (needs a numeric/date key)

The ties trap (real output from practice.db). Alice has two orders on 2024‑03‑15:

order_idorder_dateamountdefault frame (RANGE)ROWS frame + tie-breaker
10032024‑02‑02300300300
10572024‑03‑1520328 ❌320 ✅
10582024‑03‑158328328

With the default RANGE frame, both same-day rows are peers and each one shows the total for the whole day. The fix is ORDER BY order_date, order_id ROWS UNBOUNDED PRECEDING.

The LAST_VALUE trap. LAST_VALUE(amount) OVER (PARTITION BY c ORDER BY d) returns the current row's amount, because the default frame ends at the current row. Fix it with ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING, or use FIRST_VALUE(...) OVER (... ORDER BY d DESC).

Named windows (less repetition)

SELECT LAG(x) OVER w, LEAD(x) OVER w
FROM t
WINDOW w AS (PARTITION BY id ORDER BY ts);

This works in SQLite, Postgres and BigQuery.

Practice problems: A1–A8 · Time: ~2.5 hours

GROUP BY rules

  • Every column in SELECT is either in GROUP BY or inside an aggregate. (SQLite and MySQL let you break this rule silently. Postgres and BigQuery don't, so don't rely on it.)
  • Aggregates ignore NULLs: COUNT(col), SUM(col) and AVG(col) all skip NULL values. COUNT(*) counts rows.
  • SUM over zero rows (or only NULLs) returns NULL, not 0. Wrap it in COALESCE(SUM(x), 0) when a group can be empty (common after LEFT JOIN).
  • Integer division: 3 / 4 = 0 in SQLite and Postgres. Write 100.0 * a / b. In BigQuery / is always float, and SAFE_DIVIDE(a, b) returns NULL instead of erroring on divide-by-zero.

WHERE vs HAVING

SELECT customer_id, COUNT(*) AS n
FROM orders
WHERE status = 'completed'   -- filters ROWS before grouping (cheap: less to group)
GROUP BY customer_id
HAVING COUNT(*) >= 4;        -- filters GROUPS after aggregation

If a condition doesn't need an aggregate, put it in WHERE.

Conditional aggregation: the most useful pattern in analytics SQL

It turns rows into columns (a pivot), computes rates, and counts several things in one pass:

SELECT month,
       COUNT(*)                                              AS total,
       SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) AS cancelled,
       AVG(CASE WHEN status = 'cancelled' THEN 1.0 ELSE 0 END) AS cancel_rate,
       SUM(CASE WHEN status = 'completed' THEN amount END)  AS completed_revenue
FROM ...
GROUP BY month;
EngineShorthand
BigQueryCOUNTIF(status = 'cancelled'), SUM(IF(cond, x, 0))
Postgres / SQLiteCOUNT(*) FILTER (WHERE status = 'cancelled')
EverywhereCOUNT(CASE WHEN cond THEN 1 END): no ELSE, so non-matches are NULL and not counted

Conditional distinct count: COUNT(DISTINCT CASE WHEN cond THEN customer_id END) (used in the cohort matrix, A8).

Distinct counts and the grain

Before writing any aggregate, ask: "What does one row of my FROM clause represent right now?"

After orders JOIN order_items, one row is one item, so COUNT(*) counts items, not orders. You need COUNT(DISTINCT o.order_id). Getting the grain wrong is the #1 source of silently wrong numbers.

COUNT(DISTINCT a, b) isn't portable. Use COUNT(DISTINCT a || '-' || b) or count rows from a SELECT DISTINCT subquery.

Aggregating an aggregate

Questions like "how many customers have N orders?" need two levels: a CTE that aggregates per customer, then GROUP BY on that result. Don't forget the zero bucket, which requires a LEFT JOIN from customers (A6).

Cohort analysis: the recipe

  1. Activity table: one row per (user, active period). Use DISTINCT.
  2. Cohort: MIN(period) per user (first purchase, or signup).
  3. Age: periods between the cohort and the activity period (month_number).
  4. Aggregate: COUNT(DISTINCT user) per (cohort, age), divided by cohort size.
  5. (optional) Pivot ages into columns with conditional aggregation.
cohort   size  m0   m1   m2   m3
2024-01    2   2    2    2    2
2024-02    3   3    2    1    2      ← read across: how a cohort decays

Month math: (y2 - y1) * 12 + (m2 - m1). BigQuery: DATE_DIFF(activity_month, cohort_month, MONTH).

Interview follow-ups to expect: Should retention be "active in month N" or "active in month N or later"? Should cohorts be by signup or by first purchase? What about the partial current month?

The six you must know

LEFT JOIN: ON vs WHERE (asked constantly)

-- ✅ keeps all customers; only completed orders are matched
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id AND o.status = 'completed'

-- ❌ silently becomes an INNER JOIN
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'completed'      -- NULL = 'completed' is not TRUE → Nora's row is removed

Rule: a filter on the right-hand table of a LEFT JOIN goes in ON. A filter on the left-hand table goes in WHERE.

After a LEFT JOIN, use COUNT(o.order_id), not COUNT(*). Otherwise an unmatched customer counts as 1.

Semi join: EXISTS

SELECT c.* FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id AND ...);

A normal JOIN would return a customer once per matching order, and then you'd need DISTINCT. EXISTS states the intent directly, stops at the first match, and never duplicates.

Anti join: NOT EXISTS, and the NOT IN NULL trap

Live demo on practice.db ("customers nobody was referred by"; referred_by contains NULLs):

SELECT COUNT(*) FROM customers
WHERE customer_id NOT IN (SELECT referred_by FROM customers);          -- 0 rows ❌

SELECT COUNT(*) FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM customers r WHERE r.referred_by = c.customer_id);  -- 10 rows ✅

Why: x NOT IN (1, 4, NULL) means x<>1 AND x<>4 AND x<>NULL. The last comparison is UNKNOWN, so the whole condition is never TRUE. Always use NOT EXISTS (or LEFT JOIN ... WHERE right.key IS NULL).

Self joins

-- employee → manager
FROM employees e JOIN employees m ON m.emp_id = e.manager_id

-- unordered pairs within the same order (each pair once, no self-pairs)
FROM order_items a JOIN order_items b
  ON a.order_id = b.order_id AND a.product_id < b.product_id

Many-to-many explosion (fan-out): the silent killer

An order with 3 items and 2 payments:

orders ⋈ order_items ⋈ payments  →  3 × 2 = 6 rows for that order

Real output from practice.db, naive double join:

order_idtrue amountSUM(items) after joinSUM(payments) after join
1004376752 (×2)1128 (×3)
10134609201380

The fix: pre-aggregate every child table to the parent's grain in a CTE, then join 1-to-1:

WITH items AS (SELECT order_id, SUM(quantity*unit_price) AS items_total FROM order_items GROUP BY order_id),
     pays  AS (SELECT order_id, SUM(amount) AS paid_total FROM payments GROUP BY order_id)
SELECT o.order_id, i.items_total, p.paid_total
FROM orders o LEFT JOIN items i USING (order_id) LEFT JOIN pays p USING (order_id);

Interview habit: before joining, say the grain of each table out loud: "orders is one row per order, items is one row per order-line, so this join fans out to line level." Always sanity-check with COUNT(*) before and after a join.

COUNT(DISTINCT) can hide fan-out for counts, but it can't fix SUMs. SUM(DISTINCT amount) is wrong too, because two different payments can have equal amounts.

04 · CTEs and Multi-Stage Queries

How to use this chapter: read the concepts, then for each problem write your query on paper (or just in your head) before opening Show answer. The comments inside each answer explain the trap it's testing. The tables used are described in 00 The Practice Data.

Practice problems: C1–C5 · Time: ~2 hours

Why CTEs

Hard SQL problems are four to six small problems in a row. CTEs let you solve them one named step at a time, and interviewers read them easily.

WITH
step1 AS (...),          -- clean / filter the base rows
step2 AS (... FROM step1),   -- aggregate to the right grain
step3 AS (... FROM step2),   -- window: rank, lag, running totals
step4 AS (... FROM step3)    -- filter on the window result
SELECT ... FROM step4 JOIN ...;  -- attach labels, final shape

A method for 4–6 stage problems

  1. Restate the output: "one row per ___ with columns ___." This defines the final grain.
  2. Walk backwards: what table would make the final SELECT trivial? What would make that table trivial?
  3. Name each CTE for what one row means: customer_month_revenue, not t2.
  4. Build and run incrementally: SELECT * FROM step2 LIMIT 20 before writing step 3. In an assessment, this is how you catch fan-out and NULL bugs early.
  5. Aggregate first, window second, filter last. Anything computed "over all X" (totals, previous month, ranks) must be computed before you filter X down.

That last rule shows up in C3 (the category total must be computed before keeping the rank-1 row) and in X1 (previous-month revenue must come from the full table, not from the top-3 subset).

Recursive CTEs

WITH RECURSIVE r AS (
    <anchor query>              -- starting rows
    UNION ALL
    <step query referencing r>  -- repeats until it returns no rows
)
SELECT * FROM r;

Use 1: date spines (so missing days and months show up as 0):

WITH RECURSIVE days(day) AS (
    SELECT '2024-03-01'
    UNION ALL
    SELECT date(day, '+1 day') FROM days WHERE day < '2024-03-31'
)

BigQuery doesn't need recursion here: UNNEST(GENERATE_DATE_ARRAY('2024-03-01', '2024-03-31')), or GENERATE_DATE_ARRAY(start, end, INTERVAL 1 MONTH) for months.

Use 2: hierarchies: org charts, category trees, bill of materials (C2). Add a depth limit (WHERE level < 20) if the data might contain cycles.

CTE vs subquery vs temp table

  • CTE: readability; reference it several times in one query. (Some engines recompute it on each reference. BigQuery does, so mention cost if a CTE is referenced many times.)
  • Subquery: fine for a one-off EXISTS / IN.
  • Temp table: reused across several statements, or when you want to materialise an expensive step.

Daily and monthly aggregation

Aggregate by the truncated date. Missing periods simply don't appear, so a "daily revenue" chart silently skips zero days. When the question involves rolling windows, "previous period" or "consecutive" periods, build a spine (a calendar CTE) and LEFT JOIN onto it.

Rolling windows

Three correct approaches:

-- A. spine + ROWS (rows = days only because the spine has every day)
SUM(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)

-- B. no spine, value-based frame (needs a numeric order key)
SUM(revenue) OVER (ORDER BY julianday(day) RANGE BETWEEN 6 PRECEDING AND CURRENT ROW)
--    BigQuery: ORDER BY UNIX_DATE(day) RANGE BETWEEN 6 PRECEDING AND CURRENT ROW

-- C. range self-join: the ONLY way for rolling COUNT(DISTINCT)
FROM spine d LEFT JOIN user_days u ON u.day BETWEEN date(d.day,'-6 days') AND d.day
GROUP BY d.day   -- COUNT(DISTINCT u.user_id)

Two traps:

  • ROWS 6 PRECEDING on data with missing days covers more than 7 days.
  • Filtering to the report period before the window starves the first days of history. Filter after (D2).

Gaps and islands

Gaps (breaks between events): LEAD(day) and compare with the current day (D6).

Islands (consecutive runs): the key trick.

day − ROW_NUMBER() = constant within a run of consecutive days

Real output (user 1):

Then GROUP BY user, group_key gives start MIN(day), end MAX(day) and length COUNT(*). Always DISTINCT the days first: two logins on one day break the arithmetic.

Sessionization: the general "new group when X" pattern

-- 1. flag: does this row start a new group?
CASE WHEN ts - LAG(ts) OVER (PARTITION BY user ORDER BY ts) <= 30 min THEN 0 ELSE 1 END
-- 2. group id = running sum of flags
SUM(flag) OVER (PARTITION BY user ORDER BY ts ROWS UNBOUNDED PRECEDING)
-- 3. GROUP BY user, group id → start, end, event count, duration

The first row's LAG is NULL, so the comparison is NULL, it falls to ELSE, and the row is correctly flagged as a new session. The same pattern handles "new trip when the gap exceeds 1 hour", "new price regime when price changes", "new streak when a day is missed", and so on.

Ask in the interview: Is the boundary > or >= 30 minutes? Do sessions split at midnight? Is there a maximum session length?

07 · Cheatsheet

Read this the night before and the morning of the assessment.

Before you write a line: clarifying questions

  • Ties? → ROW_NUMBER (exactly one) / RANK (keep ties, with gaps) / DENSE_RANK (Nth value)
  • "Previous" = previous row or previous calendar period? Missing periods → spine or exact-period join
  • NULLs? In the data, in NOT IN subqueries, in SUM over empty groups
  • Boundaries: > or >=? Inclusive end date? Timestamps → half-open >= start AND < end
  • Definitions: active? valid? revenue (which statuses)? new vs returning?
  • Grain: what is one row of the output? Of each input table?

Show answer 
WITH clean_stats AS (                                   -- 1. latest load only
    SELECT *
    FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY stat_date, campaign_id
                                       ORDER BY load_id DESC) AS rn
          FROM ad_stats)
    WHERE rn = 1
),

    SELECT campaign_id,
           SUM(impressions) AS impressions,
           SUM(clicks)      AS clicks,
           SUM(cost_micros) / 1e6 AS spend
    FROM clean_stats

),

    SELECT campaign_id, COUNT(*) AS conversions, SUM(conv_value) AS conv_value

SELECT s.campaign_id, c.name, s.impressions, s.clicks,  -- 4. join two SAME-grain tables

       ROUND(s.spend / NULLIF(s.clicks, 0), 2)                   AS cpc,

       ROUND(COALESCE(v.conv_value, 0), 2)                       AS conv_value,
       ROUND(COALESCE(v.conv_value, 0) / NULLIF(s.spend, 0), 2)  AS roas

-- 4. 100 * clicks / impressions is INTEGER division in SQLite/Postgres -> 100.0.
-- 5. Campaign 41 never converts: LEFT JOIN + COALESCE, or it disappears.

Self-test: answer out loud

  1. Why is AVG(ctr) wrong for a weekly CTR? Give the correct formula.
  2. A table has two rows for the same day and campaign. Name two ways that can happen and how you'd make the pipeline stop producing them.
  3. Stats are one row per day; conversions are one row per conversion. What happens if you join them and then SUM(clicks)?
  4. What's the difference between "within 7 days" in hours and in calendar days? Which would you ask the stakeholder about?
  5. Why are SCD2 intervals stored half-open (valid_to exclusive)?
  6. In G8, which filter goes before the window function and which after? Why?
Show answers
  1. A rate over a group is SUM(clicks) / SUM(impressions). Averaging daily rates weights every day equally, regardless of traffic.
  2. A retried batch job that appends instead of overwriting; a stream with at-least-once delivery; a backfill overlapping a regular run. Fix: idempotent writes (MERGE on the natural key, or overwrite the whole date partition), plus a uniqueness data-quality check that fails the pipeline.
  3. Fan-out: each day's clicks are repeated once per conversion. Always aggregate each fact table to a shared grain first.
  4. 168 hours from the click timestamp vs "conversion date minus click date ≤ 7". They disagree near the boundary. Ask which one Ads reporting uses and document it in the design doc.
  5. So consecutive versions tile the timeline with no overlap and no gap: exactly one version matches any date using >= from AND < to.
  6. Share-of-spend is computed over all campaigns, before the click filter. The rank is computed after the click filter, so only eligible campaigns compete.

Chapter summary

  • Rates (CTR, CPC, ROAS) are always ratios of sums, recomputed at the reporting grain.
  • Money in Ads data is often in micros; divide by 1e6.
  • Clean first: dedupe re-run loads (latest load_id) and duplicate stream deliveries (conversion_id).
  • Two facts at different grains (daily stats, per-conversion) → aggregate each, then join.
  • Missing days need a spine; zero rows need NULLIF/SAFE_DIVIDE.

Trees and graphs: BFS and DFS

Interview reports for this role mention "islands in a binary tree" and "arrays, lists, graphs", so expect at least one traversal question. Almost all of them are one of two templates.

Vocabulary: a graph is nodes plus edges (friendships, table lineage, pipeline dependencies). A tree is a graph with no cycles and one root. Each node has children, and a binary tree has at most two. A grid is a graph whose nodes are cells and whose edges go to the 4 neighbours.

BFS (breadth-first search) uses a queue and explores in rings: everything 1 step away, then 2 steps, and so on. Use it for shortest paths in unweighted graphs and for level-by-level tree questions.

from collections import deque
seen = {start}
queue = deque([start])
while queue:
    node = queue.popleft()
    for nxt in neighbours(node):
        if nxt not in seen:          # mark when ADDING, not when popping
            seen.add(nxt)
            queue.append(nxt)

DFS (depth-first search) uses a stack (or recursion) and goes as deep as possible first. Use it for "visit everything connected", counting components/islands, tree properties (depth, paths, sums) and cycle detection.

def depth(node):                     # recursive DFS on a tree of (value, left, right)
    if node is None:
        return 0
    _, left, right = node
    return 1 + max(depth(left), depth(right))

Recognise the pattern:

Question sounds like…Use
"number of islands / connected groups / clusters"loop over nodes, DFS or BFS from each unvisited one, count the starts
"shortest / fewest steps / degrees of separation"BFS
"level by level", "nodes at depth k"BFS with a per-level loop
"height, path sum, does a path exist, validate the tree"recursive DFS
"order tasks with dependencies", "detect a cycle"topological sort (P7)
"shortest path with weights"Dijkstra (BFS with a heap)

Always mention: the complexity is O(V + E) (every node and edge once); the seen set prevents infinite loops on cycles; and recursive DFS can hit Python's ~1000-deep recursion limit, so use an explicit stack for deep inputs.

P1 · Latest state per key (CDC compaction)

changes is a list of dicts from a change-data-capture stream, in ARRIVAL order (not change order): {"id": int, "seq": int, "op": "I"|"U"|"D", "data": ...}. seq is the true order of changes for that id. The same change can arrive twice. Return the current state: a list of (id, data) for every id whose latest change (highest seq) is not a delete, sorted by id.

Example

  [{"id": 1, "seq": 2, "op": "U", "data": "b"}, {"id": 1, "seq": 1, "op": "I", "data": "a"}]
  -> [(1, "b")]
Show answer 
def latest_state(changes):
    latest = {}                                   # id -> change with the highest seq
    for ch in changes:
        cur = latest.get(ch["id"])
        if cur is None or ch["seq"] > cur["seq"]:
            latest[ch["id"]] = ch
    return sorted((i, ch["data"]) for i, ch in latest.items() if ch["op"] != "D")
# One pass, O(n) time, O(distinct ids) memory. Arrival order never matters
# because we compare seq, and duplicates are harmless (same seq -> no update).
# The SQL version is X3: ROW_NUMBER() OVER (PARTITION BY id ORDER BY seq DESC) = 1.

events is an UNSORTED list of (user_id, ts) where ts is in seconds. A new session starts when a user's event is MORE than 1800 seconds after their previous event (exactly 1800 stays in the same session). Return a dict {user_id: number_of_sessions}.

        by_user[user].append(ts)

P7 · Pipeline DAG execution order (topological sort)

deps is a dict {task: [tasks it depends on]}. Every task appears as a key. Return a list of all tasks in an order where each task comes after all of its dependencies. When several tasks are ready at the same time, take them in alphabetical order (so the answer is unique). If there is a cycle, raise ValueError.

Example

 {"report": ["clean"], "clean": ["extract"], "extract": []}
         -> ["extract", "clean", "report"]
Show answer 
import heapq

def run_order(deps):
    indegree = {t: len(d) for t, d in deps.items()}
    children = {t: [] for t in deps}
    for task, parents in deps.items():
        for p in parents:
            children[p].append(task)
    ready = [t for t, n in indegree.items() if n == 0]
    heapq.heapify(ready)
    order = []
    while ready:
        t = heapq.heappop(ready)
        order.append(t)
        for c in children[t]:
            indegree[c] -= 1
            if indegree[c] == 0:
                heapq.heappush(ready, c)
    if len(order) != len(deps):
        raise ValueError("cycle detected")
    return order
# Kahn's algorithm: repeatedly run tasks with no unfinished dependencies.
# If some tasks never become ready, they are on a cycle. O(V + E) (+ log V for the heap).
# This is exactly what Airflow / Cloud Composer does with a DAG.

P10 · Flatten nested JSON

Turn a nested record (dicts and lists, like a BigQuery STRUCT / ARRAY row) into a flat dict with dotted keys. List elements use their index. Empty dicts and empty lists are kept as values (they have nothing to flatten).

Example

 {"id": 1, "geo": {"country": "IN", "city": "Hyd"}, "tags": ["a", "b"]}
  -> {"id": 1, "geo.country": "IN", "geo.city": "Hyd", "tags.0": "a", "tags.1": "b"}
Show answer 
def flatten(record):
    out = {}

    def walk(value, key):
        if isinstance(value, dict) and value:
            for k, v in value.items():
                walk(v, f"{key}.{k}")
        elif isinstance(value, list) and value:
            for i, v in enumerate(value):
                walk(v, f"{key}.{i}")
        else:
            out[key] = value

    for k, v in record.items():
        walk(v, str(k))
    return out
# Recursion on the structure: a dict/list recurses, anything else is a leaf.
# The "and value" check keeps empty containers as leaves instead of dropping them.
# Recursion depth = nesting depth, fine for real JSON (use an explicit stack for
# adversarial input).

P11 · Products frequently bought together

from collections import Counter
from itertools import combinations

def bought_together(orders, min_support):
    pairs = Counter()
    for order in orders:
        for a, b in combinations(sorted(set(order)), 2):
            pairs[(a, b)] += 1
    result = [(a, b, n) for (a, b), n in pairs.items() if n >= min_support]

P12 · Running median of a stream

values arrive one at a time (e.g. request latencies). Return a list with the median after each arrival. For an even count, the median is the average of the two middle values. Must be better than re-sorting every time.

Example

 [5, 15, 1, 3] -> [5, 10.0, 5, 4.0]
Show answer 
import heapq

def running_median(values):
    low, high = [], []            # low = max-heap (negated), high = min-heap
    out = []
    for v in values:
        heapq.heappush(low, -v)
        heapq.heappush(high, -heapq.heappop(low))      # move low's max to high
        if len(high) > len(low):
            heapq.heappush(low, -heapq.heappop(high))  # keep len(low) >= len(high)
        if len(low) > len(high):
            out.append(-low[0])
        else:
            out.append((-low[0] + high[0]) / 2)
    return out
# Two heaps: the lower half (max-heap) and upper half (min-heap), sizes differ
# by at most 1. Each insert is O(log n) instead of O(n log n) re-sorting.
# Big-data follow-up: exact medians don't parallelise well; use
# APPROX_QUANTILES in BigQuery or t-digest style sketches.

P13 · Number of islands (grid traversal)

grid is a list of equal-length strings of "1" (land) and "0" (water). An island is a group of land cells connected horizontally or vertically (not diagonally). Return the number of islands. Empty grid -> 0.

Example

 ["110", "010", "001"] -> 2
Show answer 
from collections import deque

def count_islands(grid):
    if not grid:
        return 0
    rows, cols = len(grid), len(grid[0])
    seen = set()
    islands = 0
    for r in range(rows):
        for c in range(cols):
            if grid[r][c] != "1" or (r, c) in seen:
                continue
            islands += 1                              # new island: flood-fill all of it
            seen.add((r, c))
            queue = deque([(r, c)])
            while queue:
                cr, cc = queue.popleft()
                for nr, nc in ((cr + 1, cc), (cr - 1, cc), (cr, cc + 1), (cr, cc - 1)):
                    if 0 <= nr < rows and 0 <= nc < cols and grid[nr][nc] == "1" and (nr, nc) not in seen:
                        seen.add((nr, nc))
                        queue.append((nr, nc))
    return islands
# Scan every cell; each unvisited land cell starts a new island, then BFS marks
# the whole island as seen so it's never counted again. O(rows * cols) time.
# Mark cells as seen when you ADD them to the queue, not when you pop them,
# or the same cell is queued many times.
# Recursive DFS works too, but Python's recursion limit (~1000) breaks on big grids.

P14 · Islands in a binary tree

A binary tree is given as nested tuples (value, left, right), where left and right are subtrees or None; the whole tree may be None. Values are 0 or 1. An island is a maximal group of 1-valued nodes connected through parent-child edges. Return the number of islands.

Example

 (1, (1, None, None), (0, (1, None, None), None)) -> 2
         the root and its left child form one island; the 1 under the 0 is another.
Show answer 
def tree_islands(root):
    count = 0
    stack = [(root, 0)]                    # (node, parent's value)
    while stack:
        node, parent_value = stack.pop()
        if node is None:
            continue
        value, left, right = node
        if value == 1 and parent_value != 1:
            count += 1                     # a 1 whose parent is not 1 starts a new island
        stack.append((left, value))
        stack.append((right, value))
    return count
# Key insight: in a tree, every island has exactly one "top" node, a 1 whose
# parent is 0 (or which is the root). So count those tops. One DFS pass, O(n).
# Iterative DFS with an explicit stack avoids recursion-depth limits on
# very deep (skewed) trees. The recursive version is fine to write in an interview:
#   def walk(node, parent_is_one): ... return (starts_here) + walk(left) + walk(right)

P15 · Degrees of separation (shortest path with BFS)

graph is a dict {person: [friends]} describing an undirected network (if a lists b, b may or may not list a: treat every edge as two-way). Return the smallest number of hops from start to target, 0 if they are the same person, or -1 if there is no path or either person is unknown.

Example

 ({"a": ["b"], "b": ["c"], "c": []}, "a", "c") -> 2
Show answer 
from collections import defaultdict, deque

def degrees(graph, start, target):
    adj = defaultdict(set)
    for person, friends in graph.items():
        adj[person]                              # make sure isolated people exist
        for f in friends:
            adj[person].add(f)
            adj[f].add(person)                   # undirected
    if start not in adj or target not in adj:
        return -1
    dist = {start: 0}
    queue = deque([start])
    while queue:
        cur = queue.popleft()
        if cur == target:
            return dist[cur]
        for nxt in adj[cur]:
            if nxt not in dist:
                dist[nxt] = dist[cur] + 1
                queue.append(nxt)
    return -1
# BFS explores in rings: everyone 1 hop away, then 2 hops, ... so the first time
# we reach the target is the shortest path (unweighted edges). O(V + E).
# DFS would find A path, not the shortest. With weighted edges, use Dijkstra (a heap).
# Data-engineering twin: lineage ("how many hops from this raw table to that
# dashboard?") and identity graphs (chapter 10, M2).

In this chapter you'll learn to design warehouse tables the way interviewers expect: choose the grain, separate facts from dimensions, keep history with slowly changing dimensions, lay tables out for BigQuery, and organise layers into a Single Source of Truth. Five design exercises follow.

Why it matters: the job says "optimizing data models to ensure our Single Source of Truth remains robust and performant" and "data warehouse technical architectures". Expect a round where you're asked to design tables for a business problem and defend the choices: grain, keys, how history is kept, how it's partitioned.

Design exercises: M1–M5 · Time: ~3 hours

The one question that fixes most modeling mistakes: what is the grain?

Grain = what one row means. Say it out loud before drawing any table: "one row per campaign per day", "one row per click", "one row per customer as of today". Every bug on chapters 03 and 08 (fan-out, double counting) is a grain mismatch.

Normal forms in one breath: 1NF has atomic values and no repeating groups. 2NF means no column depends on only part of a composite key. 3NF means no column depends on another non-key column (e.g. advertiser_name belongs in advertisers, not in campaigns). The warehouse deliberately breaks 3NF for read speed. Say that you know you're doing it.

Dimensional modeling (Kimball): facts and dimensions

  • Fact table: measurements of events: numbers you SUM. Narrow and very long. Holds foreign keys to dimensions plus measures.
  • Dimension table: the context: who, what, where, when. Wide and relatively short. Holds descriptive attributes you GROUP BY and filter on.

Measures by additivity (asked surprisingly often):

KindCan SUM across…Examples
Additiveevery dimensionclicks, impressions, cost
Semi-additivesome dimensions, not timeaccount balance, active campaigns count (you can't SUM Monday's and Tuesday's balance)
Non-additivenothing: recompute from partsCTR, CPC, ROAS, averages, distinct counts

So: store the components (clicks, impressions), not the ratio. A table that stores only ctr can never be correctly rolled up to week or advertiser.

Star vs snowflake: a star has dimensions denormalised into one table each (dim_campaign includes advertiser name and vertical). A snowflake normalises dimensions (dim_campaign → dim_advertiser → dim_vertical). Stars are simpler and faster to query; snowflakes save space and ease updates. In BigQuery, stars (or one wide table) usually win.

Conformed dimensions: the same dim_advertiser used by every fact table, so "revenue by advertiser" from billing and "clicks by advertiser" from ads stats line up. This is the backbone of a Single Source of Truth.

Keys:

  • Natural/business key: the id from the source (campaign_id).
  • Surrogate key: a warehouse-generated key (an integer or FARM_FINGERPRINT hash) that identifies one version of a dimension row. You need it for SCD Type 2, because the natural key repeats across versions.

Modeling in BigQuery specifically

  • Denormalise with nested and repeated fields. One order row can hold ARRAY<STRUCT<product_id, qty, price>> for its items. That removes a join, and the items are stored next to the order. Query with UNNEST.
  • Partition the big fact tables by date (PARTITION BY stat_date). Queries filtered on it scan only those days, which cuts cost and time. Set require_partition_filter = TRUE on huge tables.
  • Cluster by the columns you filter or join on most (CLUSTER BY advertiser_id, campaign_id, up to 4 columns).
  • Joins to small dimensions are cheap (broadcast). Joins between two huge tables are what you design away.

Layers: raw → clean → curated (how a Single Source of Truth is built)

 sources ─▶ RAW / landing ─▶ CLEAN / conformed ─▶ CURATED / marts ─▶ dashboards, ML, Data Scientists
           (as delivered,    (typed, deduped,      (star schemas,
            append-only,      validated, keys       certified metrics,
            replayable)       conformed)            documented owners)

(Also called bronze/silver/gold, or staging/intermediate/marts.) Why the layers exist:

  • Raw is immutable, so you can always rebuild downstream after fixing a bug (a backfill).
  • Clean is where dedupe, type-casting, validation and conformed keys happen, once, instead of in every dashboard.
  • Curated is the SSoT: one certified table per business concept, one definition per metric ("revenue = completed orders, net of refunds"), an owner, documentation, SLAs and data-quality checks.

What makes a Single Source of Truth actually "single": a metric is defined once (in the curated table or a semantic layer such as LookML), everyone queries it instead of re-deriving it, it reconciles to the system of record (e.g. billing), and it has freshness and quality guarantees people can see.

Design exercises

M1 · Model Google Ads performance reporting

gTech teams need daily reports: impressions, clicks, cost, conversions by advertiser, campaign, ad group, device and country, for the last 3 years. Analysts slice by any of these and by week, month and quarter.

Show answer

Clarify: freshness (daily vs hourly)? Do conversions get restated later (late conversions, fraud/invalid-click adjustments)? Attribution model? Which currency? How many rows a day (say 50M campaign×device×geo rows per day)?

Grain: fact_ad_performance_daily: one row per date × ad_group × device × country. Store additive measures only: impressions, clicks, cost_micros, conversions, conv_value.

Dimensions: dim_date (date, week_start, month, quarter, fiscal periods, holiday flags); dim_advertiser (SCD2: account manager, vertical and tier change over time); dim_campaign (SCD1 for name, SCD2 for budget, bidding strategy and status); dim_ad_group; dim_geo; dim_device.

Physical design: partition the fact by stat_date, cluster by advertiser_id, campaign_id. Optionally denormalise advertiser_id and campaign_id into the fact so the common filters need no join.

Aggregates: a campaign_daily rollup and a advertiser_monthly rollup (materialised views or scheduled tables) for dashboards. They must be built from the base fact so the numbers always agree.

Restatements: conversions for a date keep arriving for up to N days. Reprocess a rolling window (e.g. the last 30 days of partitions) daily with partition overwrite, and show the "data is final after X days" rule in the dashboard.

Why not store CTR? It's non-additive. It's computed in the view or semantic layer as SUM(clicks)/SUM(impressions).

M2 · Model a Customer Data Platform (CDP) profile

Customers interact through many channels: website (cookie id), app (device id), CRM (email), support tickets (phone). Build a unified profile: one row per real customer with their identifiers, lifetime value and last activity.

Show answer

Core problem: identity resolution. Records share identifiers pairwise (the app login links device↔email, the CRM links email↔phone). A person = a connected component of the identifier graph.

Tables:

  • identity_edges(id_a, id_type_a, id_b, id_type_b, source, first_seen, last_seen): every observed link.
  • identity_map(identifier, id_type, customer_key, valid_from, valid_to): output of the resolution job. Every identifier maps to one customer_key.
  • customer_profile(customer_key, emails ARRAY<STRING>, devices ARRAY<STRING>, first_seen, last_seen, lifetime_value, consent STRUCT<ads BOOL, email BOOL>, updated_at): one row per customer, nested arrays for identifiers.
  • fact_customer_event(event_ts, customer_key, identifier, channel, event_type, value): partitioned by date.

Resolution algorithm: connected components (union-find in Python for small data; iterative label propagation in SQL or Spark GraphFrames at scale: every node takes the minimum label of its neighbours, repeat until nothing changes). Add guard rails: ignore "super-nodes" like a shared office IP or a test email that would merge thousands of people.

Stability: when two components merge, the customer_key of one changes. Keep a key-mapping history (SCD2 on identity_map) so downstream facts can be re-keyed. Pick the new key deterministically (e.g. the oldest key survives).

Privacy (say this unprompted at Google): store consent per purpose. Hash or tokenise PII (email → SHA-256 with a salt, or tokenisation), restrict raw PII to a locked dataset, and support deletion requests (the "right to be forgotten") by being able to find and purge every row for a customer, including in the raw layer and backups within the retention policy.

M3 · Write the SCD Type 2 load for dim_campaign (BigQuery MERGE)

staging_campaign has today's snapshot from the source: one row per campaign (campaign_id, name, status, daily_budget_micros). dim_campaign is SCD2. Write one statement that closes changed rows and inserts new versions and brand-new campaigns.

Show answer 
DECLARE load_ts TIMESTAMP DEFAULT CURRENT_TIMESTAMP();

MERGE ads.dim_campaign T
USING (
  WITH src AS (
    SELECT *, FARM_FINGERPRINT(TO_JSON_STRING(STRUCT(name, status, daily_budget_micros))) AS row_hash
    FROM ads.staging_campaign
  )
  -- copy 1: keyed on campaign_id -> matches the current version (closes it if changed)
  SELECT campaign_id AS merge_key, * FROM src
  UNION ALL
  -- copy 2: NULL key never matches -> inserts the NEW version of changed campaigns
  SELECT NULL AS merge_key, s.*
  FROM src s
  JOIN ads.dim_campaign d
    ON d.campaign_id = s.campaign_id AND d.is_current AND d.row_hash != s.row_hash
) S
ON T.campaign_id = S.merge_key AND T.is_current
WHEN MATCHED AND T.row_hash != S.row_hash THEN
  UPDATE SET is_current = FALSE, valid_to = load_ts
WHEN NOT MATCHED THEN                       -- brand-new campaigns (copy 1) + new versions (copy 2)
  INSERT (campaign_sk, campaign_id, name, status, daily_budget_micros, row_hash,
          valid_from, valid_to, is_current)
  VALUES (FARM_FINGERPRINT(CONCAT(CAST(S.campaign_id AS STRING), CAST(load_ts AS STRING))),
          S.campaign_id, S.name, S.status, S.daily_budget_micros, S.row_hash,
          load_ts, NULL, TRUE);

Things to say:

  • The row_hash avoids comparing every column and ignores no-op updates.
  • The UNION ALL trick is needed because one MERGE row can't both UPDATE and INSERT.
  • It's idempotent: running it twice changes nothing the second time (hashes now match).
  • Deleted campaigns (in the dim but missing from staging) need a policy: add WHEN NOT MATCHED BY SOURCE AND T.is_current THEN UPDATE SET is_current = FALSE, valid_to = load_ts. But only if staging is a full snapshot, never an incremental one.
  • Staging must be unique per campaign_id. Assert that first, or MERGE fails ("UPDATE/MERGE must match at most one source row").

M4 · Normalise or denormalise?

An interviewer shows orders(order_id, customer_id, customer_name, customer_country, product_ids STRING "4,7,9", total) in an app database and asks what's wrong. Then asks how you'd model the same data in BigQuery.

Show answer

In the OLTP app: product_ids as a comma string breaks 1NF (you can't join or index it) → order_items(order_id, product_id, qty, unit_price). customer_name/country depend on customer_id, not the order (a transitive dependency, breaking 3NF) → move to customers, or a name change must update every order.

In BigQuery: denormalise on purpose. orders gets items ARRAY<STRUCT<product_id INT64, qty INT64, unit_price NUMERIC>> and a snapshot of customer attributes as of the order (that's often what analysts want anyway), partitioned by order_date. Keep dim_customer (SCD2) for current attributes. The trade-off is read speed and simpler queries vs storage and update cost. Storage is cheap and warehouse data is append-mostly.

M5 · "Revenue in Dashboard A doesn't match Dashboard B"

A stakeholder escalates: two dashboards show different March revenue for the same advertiser. How do you investigate, and how do you stop it from happening again?

Show answer

Investigate (narrow it down, don't guess):

  1. Get both SQL definitions / lineage. Check they read the same source table and version.
  2. Compare definitions: statuses included (refunds? cancelled?), currency conversion, time zone (the advertiser's vs UTC: "March" differs by hours), the date used (click date vs conversion date), and the attribution model.
  3. Compare filters and grain: test accounts, invalid-click adjustments, a join fanning out (the count of rows per key), an inner join dropping rows.
  4. Freshness: one dashboard may cache or be a day behind; late conversions restate numbers.
  5. Diff day by day, then campaign by campaign, until the gap is isolated to specific rows.

Prevent: one certified metric definition in the curated layer (or semantic layer), both dashboards built on it, a reconciliation check against the billing system of record, documented time zone/currency rules, and a visible "last updated / data final after N days" note. Then write it up: the root cause, the fix, and how to detect it next time (a blameless postmortem).

Self-test

  1. What's the grain of a periodic snapshot fact table? Give an Ads example.
  2. Name a semi-additive measure and a non-additive measure.
  3. When do you need a surrogate key?
  4. SCD1 vs SCD2: which one should hold an advertiser's account manager if gTech measures manager performance by quarter?
  5. Why keep a raw, immutable layer?
Show answers
  1. One row per entity per period, e.g. one row per campaign per day with that day's impressions, clicks and cost.
  2. Semi-additive: an account balance or a count of active campaigns (you can't sum across days). Non-additive: CTR, ROAS, distinct users.
  3. When the natural key isn't unique in the table, as with SCD2 versions. Also for integrating several sources with clashing ids.
  4. SCD2. Quarterly results must be credited to whoever was the manager at the time.
  5. To rebuild everything downstream after a bug fix or logic change (backfill), and for audits.

Chapter summary

  • Grain first: say what one row means before anything else.
  • Facts hold additive measures; dimensions hold descriptive context. Store components, not ratios.
  • SCD2 (valid_from/valid_to/is_current + surrogate key) keeps history for point-in-time reporting; load it with an idempotent MERGE.
  • Warehouses denormalise on purpose. In BigQuery, use nested/repeated fields, and partition by date and cluster by ids.
  • A Single Source of Truth = layered (raw → clean → curated), one definition per metric, reconciled, owned, monitored.

11 · Building Pipelines: ETL/ELT, Idempotency and Data Quality

In this chapter you'll learn how data actually moves from a source system into a trusted table, and what goes wrong on the way. By the end you should be able to explain ETL vs ELT, design a load that can be re-run safely, handle late and duplicate data, write data-quality checks, and debug a "the numbers are wrong" escalation calmly and in order.

Why it matters for this role: the first responsibility in the job description is "design, develop, test, and maintain reliable and scalable data pipelines and ETL/ELT architectures", and the last is "advocate data quality… resolving complex bugs and support escalations". This chapter is the heart of the job.

11.1 What a pipeline is, in one picture

Every pipeline, from a 20-line cron script to a Google-scale system, has the same five parts:

When an interviewer says "design a pipeline", walk through these boxes in order. When something breaks, it breaks in one of these boxes, so walk through them in order when debugging too.

11.2 ETL vs ELT

ETL (Extract, Transform, Load) transforms the data before it reaches the warehouse, on a separate processing engine (a Spark cluster, a Dataflow job, a custom Python service). It was the classic approach when warehouse compute was expensive and limited.

ELT (Extract, Load, Transform) loads raw data into the warehouse first, then transforms it with SQL inside the warehouse. Modern warehouses like BigQuery have near-unlimited compute and separate storage from compute, so this became the default.

I'd do the transform before loading when sensitive data must be removed first, when the logic isn't expressible in SQL, or when it's a low-latency stream."

11.3 Batch, streaming, and the space between

  • Batch: process a bounded chunk (yesterday's data) on a schedule. Simple, cheap, easy to re-run. Latency is hours.
  • Streaming: process events continuously as they arrive (Pub/Sub → Dataflow → BigQuery). Latency is seconds, but it's harder: ordering, duplicates, late data and state.
  • Micro-batch: small batches every few minutes. A common middle ground.

Pick by the freshness requirement, not by fashion. "Daily gTech reporting" is batch. "Alert an account manager within 10 minutes if a campaign's spend spikes" is streaming. Many systems do both: a fast approximate stream for alerts, and an accurate batch job that later restates the numbers. (That's the Lambda architecture. Doing everything as one stream that you can replay is the Kappa architecture.)

11.4 Full vs incremental loads

A full load re-copies the whole source table every run. It's simple and self-correcting, but impossible for billions of rows.

An incremental load copies only what changed. There are three ways to know "what changed":

  1. High-water mark: remember the largest updated_at (or id) you loaded, and next time fetch WHERE updated_at > :last_mark. Traps: rows updated in the same second as the mark (use >= plus dedupe); clocks that go backwards; deletes are invisible.
  2. Partition-based: the source is already organised by date. Load "yesterday's partition".
  3. CDC (Change Data Capture): read the database's transaction log (binlog, WAL; tools like Datastream or Debezium), which emits every insert, update and delete with a sequence number. It's the most complete and the most complex. Chapter 06 (X3, X4) taught you to turn a CDC stream into current state.

11.5 Idempotency: the most important word in data engineering

A job is idempotent if running it twice produces the same result as running it once.

Jobs will run twice. A retry after a timeout, an engineer re-triggering a failed day, and a backfill overlapping the daily run all do it. Problem G1 in chapter 08 showed the damage when a load appends on a re-run: 10 March was counted twice.

Three standard ways to make loads idempotent:

1. Overwrite the partition (the most common for daily batch). The job for date D always replaces partition D completely.

-- BigQuery: delete + insert in one transaction, or write with WRITE_TRUNCATE to table$20240310
BEGIN TRANSACTION;
DELETE FROM ads.fact_campaign_daily WHERE stat_date = @run_date;
INSERT INTO ads.fact_campaign_daily
SELECT ... FROM ads.raw_stats WHERE stat_date = @run_date;
COMMIT TRANSACTION;

2. MERGE (upsert) on the natural key: update the rows that exist, insert the rows that don't.

MERGE ads.fact_conversions T
USING (SELECT * FROM ads.staging_conversions
       QUALIFY ROW_NUMBER() OVER (PARTITION BY conversion_id ORDER BY ingested_at DESC) = 1) S
ON T.conversion_id = S.conversion_id
WHEN MATCHED THEN UPDATE SET conv_value = S.conv_value, conversion_ts = S.conversion_ts
WHEN NOT MATCHED THEN INSERT ROW;

Note the dedupe on the source side: MERGE fails if two source rows match one target row.

3. Deterministic ids + dedupe on read: stream in with at-least-once delivery, give every event a stable id, and dedupe downstream (QUALIFY ROW_NUMBER() ... = 1).

Never write INSERT INTO target SELECT ... FROM source WHERE date = today without one of these. Say this in the interview. It signals experience.

Delivery guarantees vocabulary: at-most-once (may lose data), at-least-once (may duplicate; the usual default), and exactly-once (in practice this means at-least-once delivery plus idempotent, deduplicating writes).

11.6 Late data, backfills and restatements

Late data. An event that happened on Monday can arrive on Wednesday: a phone was offline, or a conversion was reported days after the click. If Monday's partition was built on Tuesday, it's now wrong. Options:

  • Reprocess a lookback window. Every day, rebuild the last N days (e.g. 3 for stats, 30 for conversions). Combined with partition overwrite, this is simple and robust.
  • In streaming, use watermarks. A watermark is the system's estimate that "all events up to time T have arrived". Windows close at the watermark, with allowed lateness for stragglers, and triggers decide when to emit early, on-time and late results (the Beam model, chapter 12).
  • Tell consumers. "Data for day D is final after D+3."

Backfill means running a pipeline for historical dates: a new column was added, a bug was fixed, a new table was created. To do it safely:

  1. Make the job take the date as a parameter (never CURRENT_DATE() inside the logic).
  2. Make it idempotent (11.5), so backfilled dates simply overwrite.
  3. Run in batches (a week at a time), check quality for each batch, watch cost and quotas.
  4. Warn downstream owners that numbers will change, and why.

11.7 Orchestration

Pipelines are DAGs (directed acyclic graphs) of tasks: extract → load_raw → dedupe → build_fact → dq_checks → publish. An orchestrator (Apache Airflow, which is Cloud Composer on GCP; Google also has internal workflow systems) handles:

  • scheduling (daily at 02:00 UTC) and dependencies (don't build the fact until the raw load succeeded; sensors wait for upstream tables);
  • retries with backoff, for transient failures only;
  • SLAs and alerts (if the fact isn't ready by 06:00, page the on-call);
  • parameterised runs and backfills (run_date templated into every task).

Python problem P7 (chapter 09) is literally how an orchestrator orders tasks.

A minimal Airflow DAG you should be able to sketch:

with DAG("ads_daily", schedule="0 2 * * *", start_date=datetime(2024, 1, 1), catchup=False,
         default_args={"retries": 2, "retry_delay": timedelta(minutes=10)}) as dag:
    load_raw = BigQueryInsertJobOperator(task_id="load_raw", configuration={...})     # uses {{ ds }}
    build_fact = BigQueryInsertJobOperator(task_id="build_fact", configuration={...})
    dq = BigQueryCheckOperator(task_id="dq_unique_keys",
          sql="SELECT COUNT(*) = COUNT(DISTINCT CONCAT(stat_date, campaign_id)) "
              "FROM ads.fact_campaign_daily WHERE stat_date = '{{ ds }}'")
    publish = BigQueryInsertJobOperator(task_id="publish_view", configuration={...})
    load_raw >> build_fact >> dq >> publish

Notice that the data-quality check gates the publish step. Bad data never reaches the dashboard, and the failure pages a human instead of silently shipping wrong numbers.

11.8 Schema changes

Sources change their schema without asking. Plan for it:

  • Additive changes (a new nullable column) are safe if your pipeline selects columns by name, not SELECT * into a fixed target.
  • Breaking changes (rename, type change, removed column) should fail loudly at ingestion, not corrupt data silently downstream.
  • Use data contracts: an agreed schema and semantics between producer and consumer, versioned and checked in CI.
  • Semi-structured formats (JSON, Avro, Protocol Buffers, which Google uses everywhere internally) carry schemas and allow controlled evolution.

11.9 Data quality: the six dimensions and how to check each

"Data quality" in an interview must become specific, automated checks. The six classic dimensions, each with the SQL that tests it:

DimensionQuestionCheck (BigQuery SQL)
CompletenessIs anything missing?COUNTIF(campaign_id IS NULL) = 0; every expected partition exists; row count ≥ 1
UniquenessAny duplicates?COUNT(*) = COUNT(DISTINCT key) per partition
ValidityAre values allowed?COUNTIF(clicks > impressions OR cost_micros < 0) = 0; status in the allowed set
ConsistencyDo related tables agree?every campaign_id in the fact exists in dim_campaign (an anti join returns 0 rows)
Timeliness / freshnessIs it up to date?MAX(_loaded_at) > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 26 HOUR)
AccuracyDoes it match reality?reconcile totals to the system of record (billing): ABS(ours - billing) / billing < 0.001

Beyond fixed rules, add anomaly checks: today's row count or spend within, say, ±30% of the trailing 7-day average for the same weekday. That catches the failures nobody wrote a rule for, like an upstream filter that silently dropped a country.

-- Volume anomaly: today vs the same weekday average over the previous 4 weeks
WITH daily AS (
  SELECT stat_date, COUNT(*) AS n
  FROM ads.fact_campaign_daily
  WHERE stat_date BETWEEN DATE_SUB(@run_date, INTERVAL 28 DAY) AND @run_date
  GROUP BY stat_date
)
SELECT
  (SELECT n FROM daily WHERE stat_date = @run_date) AS today,
  AVG(n) AS baseline,
  SAFE_DIVIDE((SELECT n FROM daily WHERE stat_date = @run_date) - AVG(n), AVG(n)) AS pct_diff
FROM daily
WHERE EXTRACT(DAYOFWEEK FROM stat_date) = EXTRACT(DAYOFWEEK FROM @run_date)
  AND stat_date < @run_date;
-- fail the task if ABS(pct_diff) > 0.3

Where the checks go:

  • At ingestion: schema and parse errors go to a dead-letter table (don't crash, don't silently drop, like P3 in chapter 09).
  • After each transform: uniqueness and consistency.
  • Before publish: blocking checks (fail the DAG) for things that make the data wrong, and warning checks (alert only) for things that make it suspicious.
  • Continuously: freshness monitoring on the published table.

Reconciliation is the check that makes a Single Source of Truth trustworthy. Compare key totals between layers (raw vs clean vs curated) and against the system of record. Python P9 in chapter 09 is the row-level version; in SQL it's a FULL OUTER JOIN:

SELECT COALESCE(s.id, t.id) AS id,
       CASE WHEN t.id IS NULL THEN 'missing_in_target'
            WHEN s.id IS NULL THEN 'extra_in_target'
            ELSE 'value_mismatch' END AS issue
FROM source s
FULL OUTER JOIN target t ON s.id = t.id
WHERE s.id IS NULL OR t.id IS NULL OR s.value IS DISTINCT FROM t.value;

11.10 Monitoring, on-call and postmortems

A reliable pipeline has SLOs ("the daily fact is complete by 06:00 UTC on 99% of days"), dashboards (run durations, row counts, check results, cost), alerts that reach a human with a runbook ("if dq_unique_keys fails: 1. check whether the raw load ran twice…"), and a habit of blameless postmortems: what happened, the impact, the root cause, how it was detected, and action items that prevent the whole class of problem. 11.11 Debugging an escalation: a calm, repeatable method

The job says you'll resolve "complex bugs and support escalations". In an interview, when given a scenario like "the dashboard shows zero conversions for India yesterday", show a method, not guesses:

  1. Clarify and size. Which metric, which slice, since when, and how big is the gap? Who is affected? Is it still happening?
  2. Check freshness first. Did yesterday's jobs run and succeed? Is the partition there? (Half of all "wrong data" is "not there yet".)
  3. Walk the lineage backwards, comparing the same slice at each layer: dashboard → curated → clean → raw → source. The bug lives between the last layer that is right and the first that is wrong.
  4. Diff what changed. Recent code deploys, config, schema, upstream releases, a new filter, a time-zone change.
  5. Fix forward and backfill the affected partitions (idempotently). Verify with the same check that found the problem.
  6. Communicate throughout: acknowledge, give an ETA, explain in plain language, confirm the fix with the stakeholder.
  7. Prevent: add the automated check that would have caught it, and write the postmortem.

Show answer

12.1 The problem: one machine is not enough

Suppose Google Ads produces 50 TB of click logs per day and you need clicks per advertiser. One machine reads disk at maybe 200 MB/s, so it needs roughly 3 days just to read one day of data. The only way out is to split the data across many machines, process the pieces in parallel, and combine the results. Every big-data system is a different answer to three questions:

  1. Where does the data live? (a distributed file system)
  2. How is work split, and how are partial results combined? (the programming model)
  3. What happens when a machine dies? (with 1,000 machines, one dies every day)

12.2 MapReduce: the idea to understand deeply

Google published MapReduce in 2004 (Dean & Ghemawat). The insight: an enormous number of data problems fit one shape, and if you write just two small functions, the framework handles distribution, parallelism and failures for you.

input splits      MAP                SHUFFLE & SORT            REDUCE            output
(chunks of the    each record ->     all pairs with the same   f(key, [values])
 file, one per    (key, value)       key go to the SAME        -> result
 machine)         pairs              reducer, grouped by key

Word count, the "hello world" you must be able to write on a whiteboard:

def map(document):                      # runs on many machines in parallel
    for word in document.split():
        emit(word, 1)

def reduce(word, counts):               # all counts for one word arrive together
    emit(word, sum(counts))

What happens in between is the shuffle: every mapper's output is partitioned by key (usually hash(key) % number_of_reducers), sent over the network to the right reducer, and sorted so each key's values are adjacent. The shuffle is the expensive part. It's disk writes, network transfer and a sort. Nearly every performance question in big data is really "how do I shuffle less?"

Combiner: a mini-reduce that runs on each mapper's output before the shuffle. For word count, each mapper sends ("the", 5000) instead of 5,000 copies of ("the", 1). It only works when the operation is associative and commutative (sum, count, max). It does not work for a median.

Fault tolerance: the master notices a dead worker and simply re-runs its tasks elsewhere. That's safe because map and reduce are deterministic functions of their input. (Idempotency again, from chapter 11.)

The SQL connection: SELECT advertiser_id, SUM(clicks) FROM clicks GROUP BY advertiser_id is a MapReduce: map emits (advertiser_id, clicks), the shuffle groups by advertiser, and reduce sums. When you write GROUP BY in BigQuery or Spark, a shuffle like this happens under the hood.

Joins in MapReduce: the two strategies (they still exist in Spark and BigQuery)

  • Reduce-side (shuffle) join. Map both tables to (join_key, (table_tag, row)). The shuffle brings matching keys together and the reducer pairs them. It works for any sizes, but shuffles both tables.
  • Map-side (broadcast) join. If one table is small (a dimension like campaigns), copy it in full to every mapper and look each row up in memory. There's no shuffle of the big table at all. This is the single most useful optimisation to mention.

12.4 Spark: MapReduce, but in memory and with a smarter planner

Hadoop MapReduce writes to disk after every step, and a 10-step job is 10 full disk round trips. Apache Spark keeps intermediate data in memory where possible, and plans the whole chain of steps at once.

Architecture: a driver (your program; builds the plan) and executors (worker processes on the cluster; run tasks). Data is split into partitions; one task processes one partition.

Lazy evaluation: transformations (filter, select, groupBy, join) only build a plan. Nothing runs until an action (count, collect, write, show). This lets Spark optimise the whole plan: pushing filters down, pruning columns, and choosing join strategies (the Catalyst optimizer for DataFrames).

Narrow vs wide transformations, the most important Spark concept for interviews:

  • Narrow: each output partition needs data from only one input partition: filter, select, withColumn, map. No network traffic. Spark chains these together in one stage.
  • Wide: an output partition needs data from many input partitions: groupBy, join (non-broadcast), distinct, orderBy, repartition. This requires a shuffle, and every shuffle is a stage boundary.

So a Spark job = a DAG of stages separated by shuffles, and each stage = many parallel tasks.

RDD vs DataFrame: RDDs are the low-level API (arbitrary Python objects, no optimiser). DataFrames/Spark SQL have a schema and use the optimiser, so they're faster from Python. Always prefer DataFrames.

from pyspark.sql import SparkSession, functions as F, Window

spark = SparkSession.builder.appName("ads_kpis").getOrCreate()

stats = spark.read.parquet("gs://bucket/ad_stats/")          # lazy
convs = spark.read.parquet("gs://bucket/conversions/")
campaigns = spark.read.parquet("gs://bucket/campaigns/")    # small

# G1 in Spark: keep the latest load per (date, campaign)
w = Window.partitionBy("stat_date", "campaign_id").orderBy(F.col("load_id").desc())
clean = (stats.withColumn("rn", F.row_number().over(w))
              .filter("rn = 1").drop("rn"))

# G2 in Spark: pre-aggregate both facts to campaign grain, then join
by_campaign = clean.groupBy("campaign_id").agg(
    F.sum("impressions").alias("impressions"),
    F.sum("clicks").alias("clicks"),
    (F.sum("cost_micros") / 1e6).alias("spend"))
conv = (convs.dropDuplicates(["conversion_id"])
             .groupBy("campaign_id")
             .agg(F.count("*").alias("conversions"), F.sum("conv_value").alias("conv_value")))

report = (by_campaign
          .join(conv, "campaign_id", "left")
          .join(F.broadcast(campaigns), "campaign_id")          # small table: no shuffle
          .fillna(0, ["conversions", "conv_value"])
          .withColumn("ctr_pct", F.round(100 * F.col("clicks") / F.col("impressions"), 2))
          .withColumn("roas", F.round(F.col("conv_value") / F.col("spend"), 2)))

report.write.mode("overwrite").parquet("gs://bucket/reports/campaign_kpis/")   # action: runs now

Notice how the SQL you already know maps one-to-one: groupBy().agg() = GROUP BY, Window = OVER, dropDuplicates = dedupe, broadcast = map-side join, and mode("overwrite") = idempotent write.

Performance: the five things to know

  1. Shuffles are expensive. Filter and select columns early, pre-aggregate before joins, and broadcast small tables (under a few hundred MB).
  2. Partitioning. Too few partitions means idle cores and huge tasks; too many means scheduling overhead and tiny files. repartition(n) does a full shuffle and can increase the count; coalesce(n) merges partitions without a shuffle and can only decrease. Write output partitioned by date (partitionBy("stat_date")) so readers can prune.
  3. Data skew. One key has far more rows than the others (one giant advertiser, a NULL key, a "test" id), so one task runs for an hour while 999 finish in a minute. Fixes: broadcast the other side if it's small; handle the hot key separately; salting (append a random number 0–N to the hot key on the big side, replicate the small side N times, then join and aggregate twice); filter out NULL keys first. Spark 3's Adaptive Query Execution can split skewed partitions automatically.
  4. Caching. df.cache() only when a DataFrame is reused by several actions. Otherwise it wastes memory.
  5. File formats. Use columnar Parquet/ORC (read only the needed columns, with compression and predicate pushdown) over CSV/JSON. Avoid the small files problem (millions of tiny files overload metadata and slow reads) by compacting them.

12.5 Apache Beam / Dataflow (the public face of Google's Flume)

Beam's big idea: one programming model for batch and streaming. A batch is just a bounded stream.

  • PCollection: a distributed dataset (bounded or unbounded).
  • PTransform: a step. The core ones are ParDo (map/flatMap: per-element processing), GroupByKey (the shuffle), CombinePerKey (group + reduce with automatic combiner lifting), Flatten (union), and CoGroupByKey (join).
  • Windowing splits an unbounded stream into finite chunks to aggregate over: fixed (every 5 minutes), sliding (1 hour, every 5 minutes), and session (a gap-based per-key session, the streaming version of D9 and P4!).
  • Watermark: the system's estimate of event-time completeness. Triggers decide when to emit results (at the watermark, early speculative results, late updates), and allowed lateness decides how long to keep a window open for stragglers.
  • Event time vs processing time: always aggregate by when the event happened, not when it arrived.
import apache_beam as beam
from apache_beam.transforms import window

with beam.Pipeline(options=opts) as p:
    (p
     | "Read"      >> beam.io.ReadFromPubSub(topic="projects/x/topics/clicks")
     | "Parse"     >> beam.Map(parse_json)                          # ParDo
     | "Timestamp" >> beam.Map(lambda e: window.TimestampedValue(e, e["event_ts"]))
     | "Window"    >> beam.WindowInto(window.FixedWindows(300),    # 5-minute windows
                                      allowed_lateness=3600)
     | "KeyBy"     >> beam.Map(lambda e: (e["campaign_id"], e["cost_micros"]))
     | "Sum"       >> beam.CombinePerKey(sum)                       # shuffle + combiner
     | "Format"    >> beam.Map(to_row)
     | "Write"     >> beam.io.WriteToBigQuery("proj:ads.spend_5min"))

Dataflow is Google Cloud's managed runner for Beam: autoscaling, dynamic work rebalancing (which helps with skew) and exactly-once processing within the pipeline.

B1 · Explain what happens, stage by stage, when Spark runs df.filter(...).groupBy("advertiser_id").agg(F.sum("cost")).write.parquet(...).

Show answer

Nothing runs until write (an action). Catalyst builds an optimised plan: read only the needed columns from Parquet, push the filter into the scan. Stage 1 (narrow): each task reads one input partition, filters, and computes a partial sum per advertiser (map-side combine). Shuffle: partial sums are hash-partitioned by advertiser_id and sent across the network (200 shuffle partitions by default, or as tuned by AQE). Stage 2: each task receives all partial sums for its advertisers, adds them, and writes its part of the output files.

B2 · Write MapReduce pseudocode for "distinct users per country per day" from logs (ts, user_id, country).

Show answer

Two jobs (or one with a composite key):

Job 1 (dedupe):   map: emit((date(ts), country, user_id), null)
                  reduce: emit((date, country), 1)            # one output per distinct user
Job 2 (count):    map: identity                               # key (date, country), value 1
                  reduce: emit((date, country), sum(values))  # combiner OK: sum

A single job with key (date, country) and a set of user_ids in the reducer also works, but a huge country's set might not fit in memory. At huge scale, use HyperLogLog sketches (APPROX_COUNT_DISTINCT), which merge across mappers.

B3 · A join between clicks (10 TB) and campaigns (50 MB) is slow. Why, and what do you do?

Show answer

It's probably running as a shuffle (sort-merge) join, which shuffles 10 TB. Broadcast campaigns (F.broadcast, or raise spark.sql.autoBroadcastJoinThreshold), so each executor holds the 50 MB table in memory and the clicks never move. Also filter clicks to the needed dates and columns first.

B4 · One task in your job takes 2 hours; the other 399 took 3 minutes. Diagnose and fix.

Show answer

Data skew. Check the row count per key; usually one advertiser, a NULL key, or a default/test id dominates. Fixes, in order of simplicity: filter or handle NULL/junk keys; broadcast the other side if it's small; enable AQE skew-join handling; process the hot key separately and UNION the results; or salt it: add salt = rand() % N to the big side's key, explode the small side into N copies (one per salt), join on (key, salt), then aggregate away the salt.

B5 · Why can't you use a combiner to compute a median? What would you do instead?

Show answer

A combiner must be associative and commutative so partial results can be merged. The median of medians isn't the median. Options: send all values for a key to one reducer and sort (exact but heavy); use an approximate quantile sketch (t-digest, KLL, APPROX_QUANTILES in BigQuery) whose partial sketches can be merged; or a two-pass histogram approach.

B6 · In a streaming pipeline, how do you count clicks per campaign per 5 minutes when events arrive up to an hour late?

Show answer

Assign event-time timestamps; FixedWindows(5 min) keyed by campaign; a trigger at the watermark for an on-time result plus late firings; allowed_lateness = 1 hour, with accumulating panes (or discarding panes plus a downstream MERGE/sum). The sink must handle updates idempotently (e.g. write keyed by (campaign, window_start) and upsert). Events later than an hour go to a side output / dead-letter for the daily batch to pick up.

B7 · Hive table logs is partitioned by dt. Why is WHERE to_date(ts) = '2024-03-10' slow while WHERE dt = '2024-03-10' is fast?

Show answer

Partition pruning works only on the partition column itself. The first query filters on a different column (and wraps it in a function), so the engine must read every partition. The same rule applies in BigQuery: filter directly on the partitioning column, don't wrap it in functions or derive it from another column.

13.1 How BigQuery works (the 2-minute version you should be able to say)

BigQuery is the external version of Google's Dremel (paper, 2010). Four ideas explain almost everything about its performance and cost:

  1. Columnar storage. Each column is stored separately (in a format called Capacitor, on Google's distributed file system Colossus). A query reading 3 of 100 columns reads ~3% of the data. So SELECT * is the most expensive habit in BigQuery.
  2. Storage and compute are separate. Data sits in Colossus. Compute comes from a huge shared pool of workers, allocated per query in units called slots. The petabit Jupiter network connects them fast enough that data doesn't need to live on the machine computing it.
  3. Tree-shaped execution. A query is broken into stages. Leaf workers scan column chunks in parallel, and intermediate stages aggregate and shuffle (chapter 12) through a dedicated in-memory shuffle tier. That's why GROUP BY over billions of rows takes seconds.
  4. Serverless. There are no clusters, indexes or vacuuming to manage. Your levers are how much data a query reads and how the table is laid out.

Cost models:

  • On-demand: you pay per byte scanned (per TiB). The bill depends on the columns and partitions read, not on rows returned. LIMIT 10 does not reduce bytes scanned on a normal table.
  • Capacity (Editions): you reserve slots, and queries compete for them. Now the cost is time, and efficiency still matters.

Always check the dry run / "This query will process X GB" estimate before running something big.

13.2 Partitioning and clustering

Partitioning splits a table into segments, usually by date. A query filtered on the partition column reads only matching partitions (partition pruning).

  • Types: time-unit column (PARTITION BY stat_date, or DATE(event_ts); daily/hourly/monthly/yearly), ingestion time (_PARTITIONTIME), and integer range.
  • Pruning requires a filter directly on the partition column with constants or parameters: WHERE stat_date BETWEEN '2024-03-01' AND '2024-03-31'. Filtering on a different column, or a subquery result the planner can't evaluate up front, may scan everything.
  • require_partition_filter = TRUE stops accidental full-table scans.

Clustering sorts data within each partition by up to 4 columns (CLUSTER BY advertiser_id, campaign_id). Filters and joins on those columns skip blocks. Column order matters: the first column gives the most benefit. BigQuery re-clusters automatically in the background.

Rule of thumb: partition by the date you filter on almost every query, and cluster by the ids you filter or join on next.

13.3 Nested and repeated fields (STRUCT and ARRAY)

BigQuery encourages storing related data inside a row instead of in a separate table. That's the denormalisation from chapter 10, and it comes from Dremel's original design for nested Protocol Buffer data.

CREATE TABLE shop.orders (
  order_id    INT64,
  order_date  DATE,
  customer    STRUCT<id INT64, country STRING>,                          -- nested record
  items       ARRAY<STRUCT<product_id INT64, qty INT64, unit_price NUMERIC>>  -- repeated
) PARTITION BY order_date;

-- Access a STRUCT field with a dot
SELECT customer.country, COUNT(*) FROM shop.orders GROUP BY 1;

-- Flatten an ARRAY with UNNEST (a correlated CROSS JOIN: one output row per item)
SELECT o.order_id, i.product_id, i.qty * i.unit_price AS line_total
FROM shop.orders o, UNNEST(o.items) AS i;

-- Aggregate INSIDE each row without flattening the whole table
SELECT order_id,
       (SELECT SUM(qty * unit_price) FROM UNNEST(items)) AS order_total,
       ARRAY_LENGTH(items) AS n_items
FROM shop.orders;

-- Build arrays: the reverse of UNNEST
SELECT customer.id, ARRAY_AGG(STRUCT(order_id, order_date) ORDER BY order_date DESC LIMIT 3) AS last_3
FROM shop.orders GROUP BY 1;

Trap: FROM t, UNNEST(t.items) drops rows whose array is empty (it's an inner join). Use LEFT JOIN UNNEST(t.items) AS i to keep them. Also, aggregating order-level columns after UNNEST double counts (fan-out again!).

13.5 Performance and cost best practices (the interview checklist)

  1. Select only the columns you need, never SELECT * on wide tables. (Previewing a table is free.)
  2. Filter on the partition column with constants/parameters. Put clustering columns in filters and joins.
  3. Filter and aggregate early, then join. Reduce both sides before a big-to-big join.
  4. Put the largest table first and use smaller/aggregated tables on the other side. BigQuery broadcasts small tables automatically.
  5. Avoid unnecessary self-joins. Window functions usually do the job in one pass.
  6. Approximate functions when exactness isn't required: APPROX_COUNT_DISTINCT (HyperLogLog++), APPROX_QUANTILES, APPROX_TOP_COUNT.
  7. Materialise repeated expensive logic: scheduled tables, materialized views (incrementally maintained by BigQuery), and BI Engine for dashboard speed.
  8. Remember that CTEs referenced several times may be recomputed. Materialise them into a temp table if they're expensive.
  9. ORDER BY a huge result without LIMIT is expensive and usually pointless.
  10. Monitor: INFORMATION_SCHEMA.JOBS shows bytes billed, slot time and the top offenders.

13.6 Loading data into BigQuery

  • Batch load jobs from Cloud Storage (Avro, Parquet, ORC, CSV, JSON). Loads are free (they don't use query slots). WRITE_TRUNCATE on a partition (table$20240310) gives an idempotent overwrite.
  • Streaming: the Storage Write API (supports exactly-once semantics with stream offsets), or Dataflow → BigQuery.
  • External / BigLake tables query files in Cloud Storage without loading them.
  • Transfers and replication: the BigQuery Data Transfer Service (including a Google Ads connector!) and Datastream for CDC from operational databases.
  • Transform in place: scheduled queries, Dataform (SQL workflows with dependencies, tests/assertions and version control; think dbt, but native to BigQuery), and Cloud Composer (Airflow) for orchestration across systems.

Q3 · Count orders per country and ALSO total items, from shop.orders. What goes wrong with the obvious UNNEST query?

Show answer

SELECT customer.country, COUNT(*), SUM(i.qty) FROM shop.orders o, UNNEST(o.items) i GROUP BY 1 counts item rows, not orders (fan-out), and silently drops orders with no items. Fix:

SELECT customer.country,
       COUNT(*) AS orders,
       SUM((SELECT SUM(qty) FROM UNNEST(items))) AS items
FROM shop.orders
GROUP BY 1;

Q5 · Someone ran a bad UPDATE on a production table 20 minutes ago. What do you do?

Show answer

Use time travel: CREATE TABLE ads.x_restore AS SELECT * FROM ads.x FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 25 MINUTE), verify it, then swap or MERGE it back. Pause the pipelines writing to the table meanwhile, tell consumers, and afterwards add safeguards: restricted write permissions, changes deployed through reviewed pipelines instead of ad-hoc DML, and table snapshots before risky operations. Then write the postmortem.

Q6 · "Why is BigQuery fast at scanning a billion rows but slow at updating one row?"

Show answer

It's an analytical (OLAP) system: columnar, immutable storage blocks, and massive parallel scans. A single-row update means rewriting storage blocks and paying fixed query overhead. For high-rate single-row reads and writes use an OLTP/serving store (Spanner, Bigtable, Cloud SQL); in BigQuery, batch changes into periodic MERGEs.

Chapter summary

  • BigQuery = Dremel: columnar storage on Colossus, separate compute (slots), tree execution with a fast shuffle, serverless.
  • Cost and speed depend on bytes read: select few columns, prune partitions, cluster by common filters.
  • Nested STRUCT/ARRAY data with UNNEST replaces joins. Watch for fan-out and dropped empty arrays.
  • Know the GoogleSQL features: QUALIFY, COUNTIF, SAFE_DIVIDE, DATE_TRUNC, GENERATE_DATE_ARRAY, MERGE, time travel, INFORMATION_SCHEMA.
  • Know the internal names (Dremel, Flume, Spanner/F1, Mesa, Napa, Photon) and what they do. Mesa and Napa are Ads data warehouses.

14.1 The framework: seven steps, in order

Write these headings at the top of the whiteboard or doc and fill them in. Structure is half the score.

1. Clarify the requirements (5 minutes; don't skip).

  • Who consumes the output, and for what decision? (A dashboard for account managers? An ML model? External advertisers?)
  • What exactly: which metrics, at what grain, over what history?
  • Functional: inputs, outputs, and the transformations in between.
  • Non-functional: data volume and growth, freshness/latency (daily? hourly? seconds?), correctness (exact or approximate, and are restatements allowed?), availability, cost, privacy/compliance.

2. Estimate the scale (2 minutes). It decides batch vs stream and the storage choice. Example: 5M active campaigns × 3 devices × ~50 countries active ≈ tens of millions of rows a day ≈ ~10 GB/day compressed ≈ ~11 TB over 3 years. That's comfortably BigQuery-sized, and daily batch is fine.

3. Sketch the high-level flow: source → ingest → raw → transform → serve (chapter 11's picture), naming a technology per box and why.

4. Define the data model: the grain of each table, keys, partitioning/clustering, and history (SCD). (Chapter 10.)

5. Go deep on the hard part: the interviewer will steer you. Typical hard parts are dedupe/exactly-once, late data, joins at scale, identity resolution, and backfills.

6. Reliability and quality: idempotency, retries, data-quality checks and where they block, monitoring/alerting/SLOs, reconciliation, what happens when each component fails.

7. Trade-offs and extensions: what you'd do with 10× data, lower latency, or less budget; what you deliberately left out (non-goals).

Phrases that show seniority: "The grain of this table is…", "This write is idempotent because…", "I'd gate publishing on these checks…", "The trade-off here is freshness vs cost…", "As a non-goal, I won't handle… in v1", "I'd write this up in a design doc and review it with…".

S1 · Design the daily Ads performance "Single Source of Truth" for gTech

"gTech teams (account managers, analysts, data scientists) each compute campaign performance their own way from raw logs, and their numbers disagree. Design a single trusted dataset."

Show the worked design

1. Clarify

  • Consumers: account-manager dashboards (daily), analysts (ad hoc SQL), data scientists (features for models such as churn and advertiser health).
  • Metrics: impressions, clicks, cost, conversions, conversion value, and derived CTR, CPC, CPA, ROAS. Dimensions: date, advertiser, campaign, ad group, device, country, plus the account team that owns the advertiser (it changes over time).
  • Freshness: complete by 06:00 UTC for yesterday; conversions can restate for 30 days.
  • Correctness: spend must reconcile to billing within 0.1%.
  • History: 3 years. Privacy: no end-user PII needed; advertiser data is confidential, so access is by role.

2. Scale: tens of millions of rows a day at ad-group × device × country grain, about 10–20 GB/day. Batch on BigQuery.

3. Flow

 Ads serving logs ─┐                                 ┌─▶ curated.fact_ad_perf_daily ─▶ Looker dashboards
 Conversion stream ┼─▶ raw (append-only, partitioned ┼─▶ curated.dim_* (SCD2)          ─▶ analysts' SQL
 Billing system ───┤    by ingest date, replayable)  └─▶ curated.agg_advertiser_monthly ─▶ DS features
 CRM (acct owners)─┘            │
                         clean layer: typed, deduped,
                         conformed keys, time-zone rules
        orchestrated by Composer/Airflow; checks gate every publish

4. Data model

  • fact_ad_perf_daily: grain = date × ad_group × device × country. Additive measures only. PARTITION BY stat_date CLUSTER BY advertiser_id, campaign_id.
  • dim_advertiser (SCD2: account owner, tier, vertical), dim_campaign (SCD2 for budget/strategy), dim_date, dim_geo.
  • Rollups built from the fact (materialized views or scheduled tables) so they always agree.
  • A semantic layer (for example LookML, or certified views) defines CTR, ROAS etc. once. That's what makes it a single source of truth.
  • The date is in the advertiser's account time zone (that's how Ads reports), and this is documented.

5. Deep dive: correctness under re-runs and late data

  • Daily DAG, parameterised by run_date. It rebuilds the partitions for run_date − 30 … run_date using partition overwrite (idempotent), so late conversions are absorbed and retries are harmless.
  • Conversions deduped by conversion_id in the clean layer (G2, G6).
  • Stats and conversions aggregated separately to the fact's grain, then joined (no fan-out).

6. Quality and reliability

  • Blocking checks before publish: key uniqueness, no NULL keys, clicks ≤ impressions, referential integrity to dims, spend reconciles to billing (±0.1%).
  • Warning checks: volume and spend within ±30% of the same-weekday baseline, per country.
  • Freshness SLO (06:00, 99% of days), alerting to on-call with a runbook, check results stored in a table and visible on a "data health" dashboard.
  • Each row carries _load_id and _loaded_at for lineage.

7. Trade-offs and extensions

  • Grain choice: finer grain (keyword, hour) means more rows and cost. Offer it as a separate table only if there's a proven need.
  • Hourly freshness later via micro-batches or a streaming layer, with the daily batch remaining the source of truth ("fast but provisional, then restated").
  • Migration: run the old and new pipelines in parallel, reconcile until they agree, move dashboards over one by one, then deprecate the old tables (S4).

S2 · Design a Customer Data Platform (CDP) for gTech customer engagement

"We interact with advertisers through many systems: support tickets, sales CRM, product usage, training platforms, surveys. Build a unified, trustworthy view of each advertiser customer that teams and models can use."

Show the worked design

1. Clarify

  • The "customer" here is the advertiser account, and possibly the people who work at it (contacts).
  • Use cases: a 360° profile for support agents (low-latency lookup of one account), segmentation for outreach (batch), and model features (e.g. predicting who needs help, which matches the job's "predictive problem-solving").
  • Freshness: profile updates within an hour; segments daily.
  • Privacy: contacts are people, so PII, consent and retention policies apply.

2. Scale: millions of accounts, hundreds of millions of interaction events a month. BigQuery for analytics, plus a key-value serving store for lookups by id.

3. Flow

 CRM ───────┐                     ┌──────────────┐     ┌──▶ customer_profile (BigQuery, daily/hourly)
 Support ───┼─▶ raw per source ─▶ │  standardise │ ─▶ │     └──▶ export to serving store (Bigtable /
 Usage logs ┤   (CDC or batch)    │  + identity  │     │          Spanner) for agent tools, by id
 Training ──┤                     │  resolution  │     ├──▶ fact_customer_interaction (event log)
 Surveys ───┘                     └──────────────┘     └──▶ segments + ML features

4. Data model

  • identity_edges → identity resolution → identity_map(source_system, source_id, customer_key) (SCD2, because keys can merge).
  • customer_profile: one row per customer_key, with nested arrays of source ids and contacts, first/last interaction, product adoption flags, spend tier, open tickets, satisfaction score, consent STRUCT.
  • fact_customer_interaction: grain = one interaction event: (event_ts, customer_key, source, type, attributes JSON), partitioned by date, clustered by customer_key.

5. Deep dive: identity resolution

  • Deterministic matching first: the same Ads customer id, the same verified domain, or the same billing id across systems. Edges are pairs of identifiers.
  • Customers = connected components of the edge graph (union-find; at scale, iterative min-label propagation in BigQuery or Spark). Guard against super-nodes (a shared agency email that links 5,000 accounts): cap component size and route large merges to review.
  • Probabilistic matching (fuzzy name + address) only with a confidence score, and kept separate from deterministic links.
  • Stable keys: when components merge, the oldest key survives, the mapping history is kept, and consumers get notified of re-keys.

6. Quality, privacy, reliability

  • Checks: every source record maps to exactly one customer_key; the component size distribution is stable (a sudden giant component = a bad edge); profile counts are reconciled to source systems.
  • Privacy: PII in a restricted dataset, with pseudonymous keys used everywhere else; column-level access policies; consent enforced at the segment/export step; deletion requests propagate to every layer; retention limits.
  • Idempotent daily rebuild of profiles from the event log (the profile is a derived view, so it can always be recomputed).

7. Trade-offs

  • Full recompute (simple, correct, expensive) vs incremental updates (cheap, complex). Start with a full recompute daily, and go incremental when volume demands it.
  • Real-time profile updates: stream changed events and patch the serving store; the batch rebuild corrects any drift.

S3 · Alert account managers when a campaign's spend behaves abnormally

"If a big advertiser's spend suddenly drops to zero (broken tracking, disapproved ads, an exhausted budget) or spikes, their account manager should know within 15 minutes."

Show the worked design

Clarify: Which advertisers (all, or the top N)? What counts as "abnormal"? False-positive tolerance (alert fatigue is real)? Delivery channel (email, chat, ticket)?

Flow: cost events → Pub/Sub → Dataflow (Beam): parse, key by campaign, fixed 5-minute event-time windows, sum cost, allowed lateness 30 minutes → compare with the expected spend for this campaign at this hour of the week (a baseline table computed nightly in BigQuery from 8 weeks of history, loaded into the pipeline as a side input) → if outside the band (e.g. below 20% or above 300% of expected for 3 consecutive windows) → write an alert event → a notifier that dedupes (one open alert per campaign) and routes to the owner from dim_advertiser. All 5-minute aggregates also land in BigQuery for later analysis.

Hard parts to discuss:

  • "Zero spend" can't be detected by events that never arrive. You need a timer/heartbeat per active campaign (Beam stateful processing with timers), or a periodic job comparing the "expected active" list against recent windows.
  • Seasonality: use hour-of-week baselines, not a flat average.
  • Late data: the watermark delays alerts slightly; the trade-off is speed vs false alarms.
  • Idempotent alerts: key the alerts by (campaign, incident start) so replays don't send duplicates.
  • Feedback loop: let managers mark alerts useful or not, and tune the thresholds.

S4 · Migrate a legacy pipeline (the "modernization" question)

"A critical report is built by a chain of old Hive scripts and cron jobs. Nobody fully understands it, it breaks monthly, and it takes 8 hours. Plan the migration."

Show the worked design
  1. Discover: inventory the inputs, outputs, consumers and schedules. Read the code and turn the logic into documented metric definitions. Identify undocumented "features" (hard-coded exclusions, manual fixes).
  2. Design doc: target architecture (e.g. BigQuery + Dataform/Composer), data model, quality checks, rollout plan and rollback plan. Get sign-off from consumers.
  3. Build the new pipeline, idempotent and parameterised, with tests (unit tests for transformations, data checks for outputs).
  4. Parallel run and reconcile: run both for several weeks and compare outputs daily at a detailed grain. Every difference is either a bug in the new pipeline or a bug discovered in the old one. Decide each one explicitly with stakeholders.
  5. Cut over consumers gradually (one dashboard at a time), with the old pipeline still running as a fallback.
  6. Decommission: turn off the old jobs, archive their outputs, update the docs.
  7. Measure success: runtime (8h → 30min), failure rate, cost, and time-to-debug. Report it: this is your promotion story.

The interviewer is checking that you reduce risk (parallel runs, reconciliation, rollback) and communicate (consumers never get surprised).

14.2 Follow-up questions to rehearse

After any design, expect a few of these. Have a one-paragraph answer for each:

  1. What if the data grows 100×? Partition and cluster; pre-aggregate; incremental processing; approximate algorithms; separate the hot and cold paths.
  2. What if we need it in near real time? Streaming ingestion plus a windowed aggregation, keeping batch as the restating source of truth.
  3. How do you know the data is right? Checks by dimension, reconciliation to the system of record, anomaly detection, lineage.
  4. A job fails at 3 a.m. What happens? Retries for transient errors, then an alert with a runbook; publishing is blocked, so no bad data ships; after the fix, an idempotent re-run.
  5. How do you backfill two years after a logic change? A parameterised idempotent job, run in batches, validated per batch, cost-estimated first, with consumers warned.
  6. How do you handle schema changes upstream? Contracts, schema checks at ingestion, and additive-change tolerance.
  7. How would you reduce the cost? Bytes scanned: column pruning, partition filters, clustering, materialised rollups, killing unused tables and queries (use INFORMATION_SCHEMA).
  8. Where does PII live, and who can see it? A restricted dataset, pseudonymous keys elsewhere, column-level policies, retention and deletion.

15.5 Client-facing and cross-functional scenarios (gTech-specific)

gTech supports customers and works between Sales, Engineering and Product. Expect at least one scenario like these. Model answers are below. Read them, then close them and practise your own words.

K1 · "An account manager says your dashboard is wrong and the client is angry. The call is in an hour."

Show a strong answer

"First I'd acknowledge it quickly: 'Thanks for flagging it. I'm looking now and will update you within 30 minutes.' Then I'd get specifics: which metric, which client, which dates, and what number they expected and from where. I'd check freshness (did last night's jobs succeed?) and compare the same slice against the source layer. That usually shows within minutes whether it's our data, a definition difference (time zone, attribution window) or late-arriving data. Before the call, I'd give the account manager a short, plain-language summary: what we know, what we don't yet, and when we'll know. I'd avoid guessing in front of the client. If it's our bug, I'd own it, fix and backfill it, confirm the corrected numbers with the AM, and afterwards add a check so it can't recur silently, plus a short postmortem."

K2 · "Sales wants a new metric by Friday. Engineering says the data won't be reliable until next month."

Show a strong answer

"I'd find out what decision Sales needs to make on Friday. Often they need a directional answer, not a production pipeline. Then I'd propose options: (a) a clearly labelled preliminary analysis by Friday with known caveats, (b) the production-quality metric next month. I'd put the trade-off in writing to both sides, agree on it, and make sure the preliminary number doesn't quietly become the official one: it's labelled, lives outside the certified dataset, and is replaced when the real one ships."

K3 · "Explain to a non-technical account manager why the numbers for last week changed today."

Show a strong answer

"Conversions are like mail that sometimes arrives days after it was sent. When a customer clicks an ad on Monday and buys on Thursday, the purchase is credited back to Monday, so Monday's total grows as late purchases arrive. Our reports finalise after 30 days. Before then, treat recent days as 'still counting'. I'd also suggest we show a 'provisional' label on recent dates in the dashboard, so this question answers itself." (Use an analogy, skip the jargon, and end with something that prevents the confusion next time.)

K4 · "A data scientist hands you a notebook model and asks you to 'put it in production'."

Show a strong answer

This is the JD's "transition analytical prototypes… into stable, production-grade reporting environments". "I'd start by understanding what 'production' means for them: how often it runs, who consumes it, and the latency and accuracy needs. Then I'd separate the notebook into stages, replace ad-hoc data pulls with reads from certified tables, make the code parameterised and idempotent, add tests on the transformations and data-quality checks on inputs and outputs, schedule it in the orchestrator, add monitoring (input drift, output volume), and document ownership. I'd do it with the data scientist, reviewing results side by side until they match the notebook, so they trust the production version."

K5 · "Requirements keep changing halfway through your project."

Show a strong answer

"Changing requirements usually mean the underlying goal wasn't pinned down, so I'd go back to the goal: what decision is this for? I'd capture the current requirements in a short doc with explicit non-goals, agree on what's in v1, and build in small increments that stakeholders can see early (a sample table, a prototype dashboard), so changes arrive while they're cheap. For each change, I'd make the cost visible ('this adds a week; which do you want to drop?') and let the stakeholder choose."

15.6 Using AI in your development process

The preferred qualifications mention "practice using AI technologies to augment, improve, or automate the development process". Have a concrete, honest answer:

  • Where you use it: drafting SQL/Python boilerplate, explaining unfamiliar code or error messages, generating test cases and edge cases, writing documentation and design-doc first drafts, translating queries between dialects (SQLite → GoogleSQL), and summarising logs.
  • How you keep it safe: you verify everything: run it on sample data, check row counts and edge cases, and review it like a colleague's code. You never paste confidential or personal data into tools that aren't approved for it. You stay responsible for the result.
  • An example story (story #8): "I used an AI assistant to generate candidate data-quality checks for 40 tables from their schemas. I reviewed and kept about 60% of them, which saved about two days and caught a NULL issue on day one."
  • The bigger idea: AI can also be part of the pipeline: classifying support tickets, extracting fields from free text, or anomaly explanations. That connects to the JD's "AI-driven business decisions at scale". Mention evaluation: how you'd measure whether the AI output is accurate enough before relying on it.

16.5 The day before and the day of

The day before: read the ch 07 cheatsheet, the ch 08 metrics table, and every chapter summary. Skim your 8 story titles. Don't learn anything new. Prepare the logistics (travel to the office, ID, water, a notebook). Sleep.

In each interview:

  1. Listen, then restate the question.
  2. Clarify (ties, NULLs, grain, boundaries, scale, definitions) and state your assumptions out loud.
  3. Plan before coding: name the CTEs or the functions first.
  4. Think out loud; if you're stuck, say what you're considering.
  5. Test: a normal case, then edge cases. Check the row count and grain.
  6. Summarise the complexity and trade-offs, and what you'd improve with more time.

If you blank: "Let me take a moment to think about this," then go back to a small example and solve it by hand. It's completely normal, and interviewers respect a calm recovery.
